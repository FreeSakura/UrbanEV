\section{Introduction}
\label{sec:introduction}

Finishing a run is not the same as reproducing the experiment described in a paper.  A run can produce a checkpoint and a metric even when the source paper does not fully specify the target, split, preprocessing, or hyperparameters.  A well-specified method can also fail for an ordinary engineering reason and produce no comparable result.  A single ``reproduced/not reproduced'' label does not describe these cases well.

This issue matters in urban electric-vehicle (EV) charging forecasting.  Public resources cover zonal charging demand in Shenzhen, station occupancy in Paris, workplace charging sessions, and measurements collected across several cities \cite{li2025urbanev,amaraouali2024smarter,amaraouali2023parisdataset,lee2019acndata,guo2025charged}.  These resources measure different targets.  Occupancy rates, port states, session records, charging duration, and energy volume have different denominators, missing-data patterns, and practical meanings.  The associated studies also use different model families, including physics-informed graph networks, language-model formulations, exogenous-variable Transformers, linear decompositions, and pretrained forecasters \cite{qu2024pag,qu2024chatev,wang2024timexer,zeng2023dlinear,ansari2024chronos,ansari2025chronos2}.  A reported score can therefore be interpreted only when the data meaning, available information, forecast origin, and evaluation protocol are specified.

Forecasting research has long used out-of-sample and rolling-origin evaluation \cite{dawid1984prequential,tashman2000oos}.  Later work also describes leakage caused by preprocessing, unsuitable random splits, weak baselines, and metrics that do not match the task \cite{hewamalage2023pitfalls,kapoor2023leakage}.  Reproducibility programs encourage researchers to publish code, data, environment details, and reporting artifacts \cite{pineau2021reproducibility}.  Large experiment matrices still require three distinctions: incomplete disclosure versus execution failure, an oracle upper bound versus a feasible gain, and a positive result versus a predefined continuation threshold.  Without these distinctions, the same evaluation interval may be used repeatedly for tuning.

We audit one UrbanEV configuration inventory and the sequence of model experiments that followed it.  We classify configurations into six states, verify target and run identities, and evaluate each proposed extension in a fixed order.  The stages are an oracle diagnostic, forecast-origin expert prediction, strict prequential fixed fusion, learned routing, synchronous latency measurement, foundation-model teacher screening, residual distillation, and a Paris development-only teacher test.  Metrics remain locked when an artifact is incomplete or invalid.  Each model-development stage also uses a time-stamped minimum-effect rule.  The study documents how claims were matched to stored artifacts in this project; this procedure has not been validated across separate research teams.

Counting completion and exact reproduction separately gives different totals.  Of 1,224 frozen configurations, 865 have completed artifacts, but only 156 meet the joint exact-protocol-and-numerical criterion.  In the internal UrbanEV rolling evaluation, strict CAPER--TimeXer fusion reduces macro RMSE by 3.178\% relative to the strongest evaluated single model and increases batch-1 median synchronous latency by 48.86\% on the frozen laptop-GPU workload.  The learned router adds 0.443\% over the fixed reference, which is below the predefined 1\% progression rule despite a positive block-bootstrap interval.  Under the same registered rules, Chronos-2 does not qualify as the project teacher.  Residual distillation stops after a 0.119\% gain over ground-truth-only training.  Paris student training does not begin because the development-only teacher improves by 0.847\% rather than the required 1\%.  These results apply only to the tested candidates and protocols.  They do not evaluate routing, foundation models, or distillation in general.

We organize the study around four research questions:

\begin{enumerate}
    \item[\textbf{RQ1}] How many configurations are exactly reproduced, approximately recovered, trend-only, underidentified, failed, or not completed?
    \item[\textbf{RQ2}] How much of the oracle gap remains when CAPER and TimeXer are combined by strict fixed fusion or learned routing?
    \item[\textbf{RQ3}] How do the accuracy results change after including synchronous latency and a predefined minimum-effect rule?
    \item[\textbf{RQ4}] How do artifact checks, control branches, separate data storage, and stopping rules affect which claims are supported by the stored evidence?
\end{enumerate}

The paper reports four main outputs:

\begin{itemize}
    \item \textbf{A six-state configuration table.}  The table separates exact reproduction, approximate recovery, trend-only recovery, missing identification, execution failure, and non-completion for 1,224 configurations.  It shows why a completed run is not automatically an exact reproduction.
    \item \textbf{An audit checklist and artifact links.}  We group records as configurations, predictions, targets, metrics, latency measurements, or protected-storage records.  For each group, we state the identity checks, lock conditions, and claim limits used in this study.  The ledger links each main claim to its supporting artifact.
    \item \textbf{A fixed sequence of model comparisons.}  The experiments use target checks, prequential fitting, control branches, block-resampled uncertainty, and hardware-specific latency.  This sequence measures the fixed-fusion gain and shows that later routing, teacher, and distillation results remain below their predefined thresholds.
    \item \textbf{Locked metrics and protected-data controls.}  Artifact checks blocked invalid shuffled controls and corrected missing-target representation before metric access.  Paris formal and protected target-bearing files were stored separately, so only development targets contributed to the reported Paris result.
\end{itemize}

\paragraph{Claim boundary.}
This is an audit and evaluation study, not a new state-of-the-art model paper.  Its numerical results concern one UrbanEV inventory, six internal rolling folds at seed 42, one latency platform, and Paris development-only data.  UrbanEV and Paris absolute RMSE values are not compared because their panels and targets differ.  The 1\% threshold is a time-stamped project rule, not a universal definition of scientific or economic importance.  We make no claim of protected-test performance, production readiness, universal generalization, or cross-dataset superiority.  Paris formal and protected files were moved into separate storage, and that movement is reported as storage rather than analytical access.  The conclusions below are limited to the evidence available within this boundary.
